# Evaluation methodology

Results are generated by `evals/run.py` into `artifacts/runs/<run_id>/` and rendered into
`docs/results/` by `evals/report.py`. No number in this repository is written by hand.

## Corpus

| Set | Documents | Questions | Source |
|---|---|---|---|
| Synthetic | 8 PDFs (6 native, 2 scanned) | 59 (47 answerable, 12 unanswerable) | `evals/corpus/generate.py`, seeded, byte-reproducible |
| Real | IRS Publication 501 (2025, 31 pp), NASA TN D-233 (1960, 36-page scan) | 26 (22 answerable, 4 unanswerable) | U.S. Government works; see `evals/corpus/real/sources.json` |

Synthetic documents cover: two-column layout with sidebar and footnote, ruled tables, facts
that exist only inside raster images, scanned pages with skew and noise, a near-duplicate
distractor (the same report for a different year), and a document with embedded instructions
aimed at an AI assistant. Every synthetic organisation, person and number is fictional.

Real-document questions were written by reading page images, not parser output, so a parser
error cannot leak into the answer key. They were written during development with AI
assistance and have not yet been independently reviewed.

Each question has `expected_doc`, `expected_pages`, `evidence` (short exact strings that a
correct answer must contain) and, for injection cases, `forbidden` strings. Questions are
split `dev`/`test` (about one third dev) by a hash of the id. Thresholds such as the retrieval
similarity floor may be tuned on `dev` only.

## Configurations

`experiments/*.yaml`. All use k = 5 and the same parse.

| Config | Chunking | Retrieval |
|---|---|---|
| c1-fixed-dense | 1000/200 character window (the original app) | dense |
| c2-structure-dense | page-bounded sections; tables and figure text whole | dense |
| c3-structure-hybrid | as c2 | dense + Postgres full text, reciprocal rank fusion (k = 60) |
| c4-structure-hybrid-rerank | as c2 | c3, top 20 reranked by `ms-marco-MiniLM-L-6-v2` |

## Metrics

A chunk is **on target** if it is from the expected document and shares a page with
`expected_pages`. It is an **evidence hit** if it is on target and contains every evidence
string (lower-cased, non-alphanumerics removed).

| Metric | Definition | Applies to |
|---|---|---|
| Evidence hit rate @5 | share of questions with an evidence hit among the 5 retrieved chunks | answerable |
| Page hit rate @5 | share with any on-target chunk; reported to show how page overlap alone flatters large chunks | answerable |
| MRR | mean of 1/rank of the first evidence hit (0 if none) | answerable |
| Answer accuracy | answer contains every evidence string; refusals count as wrong | answerable |
| Citation precision | on-target cited chunks / cited chunks, for answered questions | answerable, answered |
| Citation hit rate | at least one cited chunk is on target | answerable, answered |
| Supported rate | answer contains the evidence and a cited chunk contains it too | answerable, answered with evidence |
| Judge grounded rate | LLM judge says every claim is supported by the cited text (online only) | answerable, answered |
| False refusal rate | refused an answerable question | answerable |
| Correct refusal rate | refused an unanswerable question | unanswerable |
| Injection followed rate | answer contains a `forbidden` string | injection |
| Latency p50/p95 | nearest-rank percentiles of wall-clock time per stage and in total, over `repeat` runs per question | all |
| Tokens | input and output tokens reported by the provider, for answers, rewrites and the judge separately | online |

## Failure categories

Each question gets at most one category, in this priority order:

1. `parse_miss`: no stored chunk on an expected page contains the evidence (a parsing/OCR or
   chunking loss; retrieval could not have succeeded).
2. `retrieval_miss`: evidence exists in the index but not in the top 5.
3. `false_refusal`: evidence was retrieved but the workflow refused.
4. `wrong_answer`: answered, but without the evidence strings.
5. `wrong_citation`: correct answer, no on-target citation.
6. `injection_followed`: the answer contains a forbidden string.
7. `missed_refusal`: an unanswerable question was answered.

## Modes

- `--llm offline`: `ExtractiveModel`, which returns the source sentence with the highest
  content-word overlap. Deterministic and network-free; used in CI. It measures the pipeline
  with a trivial reader, not LLM quality.
- `--llm gemini`: Gemini through LangChain with structured output. Temperature 0, but provider
  outputs are not guaranteed deterministic; report the run id with any number.
- `--judge`: adds the LLM groundedness judge. The judge uses a different Gemini model tier from
  the answer model, but the same vendor; it may share blind spots with the answer model, which
  is why the deterministic supported rate is reported next to it.

## Known weaknesses of these metrics

- Evidence matching is string containment. A table row with the same value as the target row
  satisfies it (observed on NASA TN D-233 Table I).
- An answer that paraphrases a number ("about forty-eight million") is scored wrong.
- 85 questions is small. A difference of one question is 1-2 percentage points; small
  differences between configurations are not meaningful.
- Real-document questions were written by the same process that built the system.

## Reproducing

```bash
docker compose up -d db
make corpus           # regenerate synthetic PDFs (optional; committed copies are identical)
make eval-offline     # all configs, offline model
make eval-online      # needs GOOGLE_API_KEY in .env; add LANGSMITH_* to trace
make report           # rebuild docs/results from the latest run
```
